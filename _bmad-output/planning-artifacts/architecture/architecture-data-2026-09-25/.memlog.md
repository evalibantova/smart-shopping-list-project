| 8 | decision | AD-1: Design paradigm — Feature-sliced SPA. Binds: all frontend source. Prevents: feature code bleeding across silos; agents touching another feature's internals. Rule: each feature owns src/features/{feature}/; components used by 2+ features live in src/components/shared/; design primitives in src/components/ui/; no direct cross-feature imports. |
| 9 | decision | AD-2: Service layer abstraction. Binds: all data reads and writes. Prevents: localStorage assumptions scattering into feature code; costly refactor at API transition. Rule: features never touch localStorage or fetch directly — they call a service function (e.g. recipeService.getAll()); services owned by one feature live in src/features/{feature}/services/; services used by multiple features (e.g. ingredientsDb) live in src/services/; hooks call the service then update Zustand — services do not touch the store. |
| 10 | decision | AD-3: REST API response shape — bare body. Binds: all PHP API endpoints and frontend service layer. Prevents: two consumers expecting different envelope shapes. Rule: success returns the resource JSON directly with appropriate 2xx status; errors return { error: "message" } with 4xx/5xx status; one apiFetch() wrapper on the frontend handles this uniformly. [ADOPTED] |
| 11 | decision | AD-4: Zustand store — one store instance composed from feature slices. Binds: all frontend state. Prevents: agent file collisions on a monolithic store file; shopping list state being stored rather than derived. Rule: each feature owns its own slice file in src/store/; src/store/index.ts composes all slices into one createStore() call; shoppingListSlice contains selectors only — no state — enforcing live-computed rule. |
| 12 | decision | AD-5: API URL structure — no versioning, /api/ prefix. Binds: all PHP routes and frontend service layer. Prevents: frontend and backend agents using different URL roots. Rule: all API routes are prefixed /api/ (e.g. /api/recipes, /api/meal-plan); versioning added as a route group prefix when a second consumer requires it. |
| 13 | decision | AD-6: PHP backend folder structure — by layer. Binds: all backend source. Prevents: agents organising files inconsistently. Rule: api/src/Actions/ (one class per endpoint), api/src/Repositories/ (DB queries per resource), api/src/Routes/ (route definitions); follows standard Slim v4 conventions. |
| 14 | decision | AD-7: Meal plan data shape — date-keyed entries. Binds: meal planner feature, localStorage schema, MySQL schema, mealPlannerSlice. Prevents: week-keyed and date-keyed representations diverging between MVP and API phases. Rule: each planned meal is a record { id, date: "YYYY-MM-DD", slot: "breakfast"|"lunch"|"dinner", recipeId, servings }; the weekly calendar UI derives its grid from these rows by filtering on date range. |
| 15 | decision | AD-8: localStorage ID generation — crypto.randomUUID(). Binds: all service layer create() functions in MVP phase. Prevents: ID collisions across records and forward collision risk when multi-user lands. Rule: every new record created in localStorage gets id: crypto.randomUUID(); MySQL auto-increment takes over when the API phase begins — no mapping needed since phases are a full swap. |
| 16 | decision | AD-9: localStorage key namespace — slist_. Binds: all localStorage reads/writes. Prevents: agents inventing inconsistent key names or colliding with other browser storage. Rule: all localStorage keys are prefixed slist_ — slist_recipes, slist_meal_plan, slist_pantry, slist_ingredients_db, slist_tags. |
| 17 | constraint | app working name: Smart Shopping List |
| 18 | decision | AD-10: Optimistic mutation flow. Binds: all write operations across all features. Prevents: inconsistent mutation patterns across features. Rule: 1) update Zustand store immediately (optimistic); 2) call service; 3) on error: roll back store state + show toast. [ADOPTED from docs/STACK.md] |
